## Listen

### 実践編 : ユーザー行動の推定・確認

ワークでは次のプロンプトを使用してください。Kiro CLI などの生成 AI ツールに次のプロンプトを与えます。

> [!IMPORTANT]
> 事前に、今回検討する顧客についてまとめたスライドが `customer.png` として `discovery` ディレクトリに保存されているか確認ください。

**🤖[Prompt 1.1]**
> `discovery/customer.png` に定義された顧客のうち、目的を達成できた顧客のインタビュー結果をまとめています。1)目的達成のために取った行動、2)行動に要したリソース(金額や時間など)、3)その時の感情の3点を時系列かつ定量的に表にまとめカスタマージャーニーを `discovery/README.md` の Listen セクションに記載してください。行動は「顧客が実際に何をしたか」が外から観察できる粒度で書いてください。リソースは後の工程で削減幅を見積もる材料になるため、金額や時間を概算でも数値で入れ、推測にもとづく値にはその旨を添えてください。

生成 AI の出力結果は誤りを含んでいたり具体性を欠いていたりします。次のような質問を投げかけることで、修正を促してください。

* 私達のサービスのユーザーは、○○する前/後に□□する必要があり、△△ぐらい時間をかけています
* 私達のサービスのユーザーでは、○○する人はほとんどいません
* 私達のサービスのユーザーでは、○○することを□□と呼んでいます

### 改善編 : ユーザー行動の修正

改善編ではモックから得られた定量、定性データがあるはずです。それらを利用し、行動を洗練するための修正を依頼してください。

* 実際のユーザーは、○○するのに不安、戸惑いを感じていました。また、X 時間はその作業にかかるようです
* 実際のユーザーは、○○をそれほど不安・不快に感じていませんでした
* 実際のユーザーは、○○を自ら行うのが困難でした。ユーザーのリテラシーについて、初心者の想定を加える必要があります


## Define

### 実践編 : 抜けもれなく問いを立てる

> [!IMPORTANT]
> 事前に、 `discovery/README.md` の "Listen" セクションが記載され保存されていることを確認してください。

洗い出された行動一つ一つを確認し、より最適・より連続なあるべき姿を発見するための問いを立てます。

**🤖[Prompt 2.1]**
> `discovery/README.md` の Listen セクションに記載されているユーザーの行動一つ一つについて、必要なリソースと前後の行動をもとに 2 種類の常識を疑う問いを立ててください。顧客が当然と受け入れている前提そのものを疑い、「その手間は本当に必要か」「その順序でなければならないのか」という観点で問いを立てます。行動をうまくこなすための改善案ではなく、その行動自体が不要になる可能性を問う形にしてください。各行動に対し立てた問いを `discovery/README.md` の Define セクションに表にまとめてください。  
> \* 「なぜ〇〇せずに□□ができないのか? 」  
> \* 「なぜ○○と○○は同時にできないのか?」

問いを立てた後、評価を行います。

**🤖[Prompt 2.2]**
> 各問いについて、解決した場合に削減あるいは得られるリソースと、顧客が問いを浮かべる頻度をもとに Top３ をランキングして追記してください。

### 改善編 : インパクトのある問いの作成

モックから得られる反応は必ずしもポジティブではない場合があります。特に課題を解決していても意思決定につながらない場合、「より最適」「より連続」についてより効果・範囲を広げた問いが立てられないか質問してください。

* 「○○せずに」について、より多くのリソースをまとめて解消することはできないか ?
* 「同時に」について、より広範囲の行動を一括して行う問いは立てられないか ?


## Invent

> [!IMPORTANT]
> 事前に、Define まで終了した `discovery/README.md` 、事前課題で作成した `discovery/solutions.md` が全員に共有されているか確認してください。

Invent を始める前に、事前準備したソリューションを評価します。

**🤖[Prompt 3.1]**
> `discovery/solutions.md` に並べられた機能を自社で実装する際の難易度を評価します。難易度は 1, 3, 5, 10 の 4 段階とし、一般的な開発工数ではなく「このチームが実際に手を動かして完成させられるか」を基準にしてください。その判断にはチームの情報が必要なため、評価の前にチームメンバーの構成・経験・学習能力等に関する質問を 3~5 個行ってください。結果は、難易度と理由を箇条書きに追加する形で記載してください。理由には、難易度を押し上げている具体的な要因（未経験の技術、依存する外部システムなど）を書いてください。

発明する主体を変えながら、ソリューションを組み合わせて発明を実施していきます。

**🤖[Prompt 3.2]**
> `discovery/README.md` の Define セクションで定義した問いのうち **「問い」** に応えることが出来る発明を `discovery/solutions.md` に記載したソリューションを複数組み合わせて行い Invent セクションに追記してください。記載は`solutions.md` の様式に倣い難易度は合計を書いてください。

> [!NOTE]
> プロンプトの一部を編集する必要がある場合(今回は「発明する主体」と「問い」)、テキストエディタ等にプロンプトをコピー、編集した後に生成 AI ツールに貼り付けると Enter による誤送信を防ぎやすいです。

作成できた発明の中から、解決できた場合のインパクトと難易度を基に一つ選択してください。

## Refine : モック構築

作成した PR/FAQ からユーザーテストに利用できるモックを生成 AI で構築します。このモックには、LP 、動作が体験できる (ダミーのレスポンスをつかったアプリケーション) が含まれます。

### モックに関わるプロジェクトの構成

```
yourwork
├── .kiro/                  # カスタムエージェント等、Kiro CLI 用設定ファイルディレクトリ
├── .claude/
│   └── skills/             # Claude Code 用のスキル（mock-builder）
├── AGENTS.md               # ツール共通の作業規約（OpenAI Codex CLI 等が読み込みます）
├── CLAUDE.md               # Claude Code 用の入口。AGENTS.md を読み込みます
├── prompt/                 # プロンプトファイルディレクトリ
│   └── prompt.md           # アプリケーション仕様記述ファイル（ツール非依存）
├── template/               # アプリケーションテンプレート
└── product/                # 生成されるアプリケーション（生成 AI ツールにより作成されます)
```

モックの仕様そのものは `prompt/prompt.md` に書かれており、ツールに依存しません。`.kiro/` `.claude/skills/` `AGENTS.md` `CLAUDE.md` は、各ツールがこの仕様書と作業規約にたどり着くための入口です。そのため、どのツールを使っても同じ仕様でモックが構築されます。

### モックの構築

> [!IMPORTANT]
> 事前に環境構築が完了しているか確認ください : [準備ガイド参照](/docs/organizer/generative_ai_setup.md)。また、項目済みのモックがある場合は削除の手順を参考に一度削除することを推奨します。モックは反応を得るための使い捨てなので、ためらいなく削除してください。

### 使用方法

#### 1. ディレクトリの移動

**`yourwork` で作業しているか確認します。いなければ、以下のコマンドを実行し、`yourwork` ディレクトリに移動します。**

```
pwd
# /your/working/directory/aws-ml-enablement-workshop/yourwork を期待
# 他のディレクトリにいれば yourwork へ移動
cd /your/working/directory/aws-ml-enablement-workshop/yourwork 
```

#### 2. Tracker システムのデプロイ（オプション）

> [!NOTE]
> この手順はオプションです。構築したモックアプリケーションの View 数や Click 数などのメトリクスを計測したい場合はデプロイしてください。

ワークショップで使用するモックアプリケーションの分析トラッカーシステムをデプロイします。このシステムはユーザーの操作を記録し、ダッシュボードで可視化します。

```bash
# AWS CLI を使用して CloudFormation スタックをデプロイ
# {任意のメールアドレス} を実際のメールアドレスに置き換えてください
# デプロイ先のリージョンはデフォルトでは東京リージョン（ap-northeast-1）になっています
aws cloudformation deploy \
  --template-file ./tracker/MLEWTrackerDeploymentStack.yaml \
  --stack-name mlew-tracker-stack \
  --parameter-overrides \
    NotificationEmailAddress={任意のメールアドレス} \
    Environment=dev \
  --capabilities CAPABILITY_IAM \
  --region ap-northeast-1
```

デプロイ実行後、指定したメールアドレスに「**MLEW Tracker Deployment Notifications <no-reply@sns.amazonaws.com>**」からメールが届きます。メール本文の「**Confirm subscription**」リンクをクリックして、SNS通知の購読を確認してください。

10～15分ほど待つと、デプロイ完了通知メールが再度届きます。メールには以下のような情報が記載されているので、控えておいてください。

```
Access Information:
----------------------
API Endpoint: https://xxxxxxxxxx.execute-api.ap-northeast-1.amazonaws.com/dev
API Key: XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
Dashboard URL: https://dxxxxxxxxxx.cloudfront.net
```

これらの情報は `4. モック構築の実行` で利用します。

#### 3. 生成 AI ツールの起動

モックの仕様書は `prompt/prompt.md` で、ツールに依存しません。各ツールの設定ファイルはこの仕様書へ案内するための入口にすぎないので、設定が効いていないと感じたときは `prompt/prompt.md` の内容を直接渡せば同じ結果が得られます。

**Kiro CLI**

以下のコマンドで Kiro CLI のモック構築用エージェントを起動します。

```
kiro-cli --agent mock-builder
```

**Claude Code**

```
claude
```

起動後、`/mock-builder` と入力してスキルを呼び出します。

**OpenAI Codex CLI**

```
codex
```

起動後、`prompt/prompt.md` のプレースホルダを埋めた上で、内容をそのまま貼り付けます。

#### 4. モック構築の実行

ツールに次の 2 つを渡すと、アプリケーションの実装が始まります。

* 実装したいアプリケーションの詳細
* （Option)トラッキング用エンドポイント等の情報（`2. Tracker システムのデプロイ` で控えた API Endpoint / API Key / Dashboard URL）

**実装したいアプリケーションの詳細については、Refine で作成した PR/FAQ を与えてください**。 

Kiro CLI のカスタムエージェントや Claude Code の `/mock-builder` スキルを使う場合は、`こんにちは` や `アプリケーションを作成したい` など適当な言葉を入力いただくと、上記の 2 点をツール側から順番に質問されます。`prompt/prompt.md` を貼り付ける場合は、該当するプレースホルダをこの 2 点で置き換えてください。Tracker をデプロイしていない場合は、トラッキングは不要と伝えるか、該当のプレースホルダを削除すれば省略できます。

渡した内容をもとにアプリケーションが自動的に実装され、CloudFront + S3 でホスティングされます。

#### 5. ホスティングしたアプリケーションの削除

AWS にデプロイしたアプリケーションを削除したい場合は、Kiro CLI などの起動中の生成 AI ツールに、`product/ ディレクトリを参照し、デプロイしたアプリケーションを削除したい` と伝えてください。
各種リソースの削除が行われます。

## Test/Iterate

### 実践編 : 社内マイルストンパート

社外顧客に確認する価値があるか社内で意思決定をするマイルストンの下地を、次のプロンプトで作成できます。

**🤖[Prompt 5.1]**
> 解決策が顧客の課題を解決し、採用の決定を行うかテストしたいと考えています。「課題解決の達成」「行動変化の達成」という 2 つのマイルストンに到達していることを ① Who:誰が ② What:どう計測し ③ How: どのような基準で判断するのかをまとめます。列にマイルストン、行に Who/What/How をとった表をTest/Iterate のセクションに作成し、`discovery/README.md` の Refine セクションで定義した解決策の評価基準を提案してください。社外の顧客に見せるべき発明を絞り込むための評価である前提とし、作成するのは表のみで構いません。What はユーザーテストの場で観測または計測できる事象に限り、How は達成・未達を後から一意に判定できる数値の基準にしてください。「満足度が高いこと」のように人によって判定が変わる基準は、絞り込みの判断に使えないため避けてください。

ユーザーテストのシナリオの台本を次のプロンプトで生成できます。

**🤖[Prompt 5.2]**
> `discovery/README.md` の Test/Iterate セクションに記載のマイルストン達成を評価するためのユーザーテストを行います。
Refine セクションの PR/FAQ を基に、目的の共有、ユーザー操作の観測、課題解決と行動変化の計測を行うための台本を Test/Iterate セクションに追記してください。

### 改善編 : 社外マイルストンパート

社外の評価を確認しリリースするか否かの意思決定をするマイルストンの下地を、次のプロンプトで作成できます。

**🤖[Prompt 5.3]**
> `discovery/README.md` の Test/Iterate セクションに記載されたマイルストンに対し、実プロダクトのリリースまでのマイルストンも追加したいと考えています。最初の熱心な顧客(ファン)の獲得、シェア推計に基づく投資判断、の 2 つのマイルストンを表の列に追加し、Refine セクションの PR/FAQ で定義した解決策の評価基準を提案してください。既存の列と Who/What/How の粒度をそろえ、社内の期待や意見ではなく社外の顧客の実際の行動で判定できる基準にしてください。シェア推計には、推計の前提とした母数を併記してください。
